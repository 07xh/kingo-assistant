# KingoAssistant · EXE 原生普通账号登录修复（2026-11-16）

## 原来为什么一直显示“登录接口未核验”

旧客户端仅有一条通用账号表单适配器，其登录前强制要求用户自行填入一系列 verified 开关、没有实际的学校临时签名请求构造。用户已提供 11 月 3 日和 11 月 14 日本人授权 HAR，其实不仅存在登录地址，还包含可在本机审查的学校一方登录前端 JavaScript。此前工作不该把这些已知信息长期停留在“协议未知”。

## 本次实际接入

学校官方网页正常账号登录使用：
- 官方 HTTPS 主机 jwmis.ncwu.edu.cn；
- GET /hsjw/cas/login.action：建立本次浏览器页面对应的会话，并获取会话/验证码要求；
- GET /hsjw/custom/js/SetKingoEncypt.jsp：确认当前请求的加密元信息；
- GET /hsjw/frame/homepage?method=getTempDeskey、getTempNowtime：**只取得本次服务器新返回的临时值**；
- POST /hsjw/cas/logon.action：按官方登录页面的正常表单生成加密请求；不使用另一条喜鹊儿登录快捷模式；
- POST /hsjw/jw/common/showYearTerm.action：用**同一 HTTP 会话**读取此前已抓到的学期 JSON，将 userCode 与本次输入的本人账号严格比较；两者完全匹配才保留应用内会话。

新模块：core/ncwu_signed_login.py（连接、挑战检查、一次提交、回读）与 core/ncwu_legacy_encoder.py（兼容现有旧格式数据编码）。HTTP 客户端不提取浏览器 Cookie，不从 HAR 复制临时密钥、签名、账号、密码；密码和本次生成的请求内容只保留在进程内，返回固定的错误码或成功状态。

### UI 行为

首页第二步改为“在 EXE 登录本人教务账号”。点击后可以输入本人账号，取消不联网；再输入密码，取消不联网。默认**不再要求用户手动把 verified 改成 true**。一旦学校明确要求图形验证码、短信验证码、统一身份认证或动态口令，当前适配器停止并提示，绝不切换到缺少挑战检查的快捷登录模式。登录后身份匹配才显示“EXE 已验证”。

当前模块使用每次点击最多六个单次官方请求；不自动重试，不跟随重定向，本机至少间隔 60 秒再次尝试，尊重服务器返回的 429 Retry-After。这是保守的本机安全保护，**不冒充学校对第三方客户端发出的正式授权或公布的流量上限**。

### 已验证和未验证

已验证：原 HAR 登录接口、正常登录 JavaScript 的参数关系、两种登录请求模式差异、学期响应字段类型；兼容编码有独立公开测试向量。CI 使用 MockTransport 完成安全用例，**不访问学校服务**。

仍需用户本人 Windows 实测：
- 当前 11 月 16 日学校是否仍支持这套正常账号签名协议、是否增加了新挑战步骤；
- 用本人账号在 EXE 内登录，是否获取官方学期接口正确 userCode；
- 本人课表动态 param/param2 合法生成方式、可选课程目录、剩余名额、当前选课时间及可操作提交接口。

**当前仍没有实现真实自动提交选课。登录成功、学期读取成功都不能等同于成功选课。**

# 自适应执行调度 V2（第一阶段：只读监测）

> 2026-11-20：本阶段是 **经授权只读查询的自适应放缓控制器**，不是新的选课提交适配器。
> 只读监测支持 opt-in；真实 NCWU 选课写协议和本人账户验收仍未完成。
> 软件不可因这次改动自动提交，更不能绕过学校访问限制。

## 复用既有执行链，而非新增“高频抢课引擎”

- `core/request_budget.py`：所有学校请求须经已核实的共享窗口配额，串行 lease 与 Retry-After 仍由其管理。
- `core/scheduler.py`：继续每轮读取一次课程目录，不按课程数量放大请求；仅这里接入自适应间隔。
- `core/enrollment_schedule.py`：继续通过本地定时 + 正式窗口检查协调，60–3600 秒的窗口轮询下限保持不变。
- `core/enrollment_flow.py`：维持一次写意图、串行提交和官方记录回读；UNKNOWN 停止，不盲目重试。
- `core/date_flip_sync.py` 与 `core/time_sync.py`：已有校时逻辑保持不变。
- `core/enrollment_schedule.py`：本地倒计时最后 1 秒改为最多每 50 毫秒检查一次（尽力而为，受操作系统调度影响），这不增加任何服务器探测次数。

## 第一阶段：实时只读压力感知

配置位于 `strategy.adaptive_polling`：

```yaml
adaptive_polling:
  enabled: false
  slow_request_ms: 2000
  budget_wait_ms: 200
  max_multiplier: 8
```

开启后，只观察已经成功完成的课程目录查询最新耗时：

1. `request_ms` 超过阈值或 `budget_wait_ms` 超过阈值，下一周期延迟倍率 ×2，直至上限；
2. 两项指标低于阈值时，倍率 ×0.75，逐步返回 1 倍原有周期；
3. 当前周期无可信耗时数据时，不推断服务器健康程度，也不更改倍率；
4. 最终间隔只能 **大于或等于** 经过 `monitor_policy.validate_limits` 验证的基准查询间隔，最大 3600 秒；
5. 原有 `pickup` 高峰日历仅决定基准间隔，不能使自适应控制器突破频率下限。

例如基准间隔 60 秒，受压后可能转为 120、240 秒，压力缓解再逐步恢复 60 秒。它绝不把 60 秒提升为每秒查询。配置中的阈值不是学校授权频率，其作用只在于进一步放缓既有监测。

## 异常 / 写入边界

- `401/403/429`、会话过期或验证码等仍沿现有校验逻辑 **停止**；429 的 Retry-After 由共享请求预算记录，不尝试规避。
- `502/503/504`、超时等由原有有限的只读 HTTP 错误路径处理；不能把错误视为课程开放，更不能无限重试。
- 请求体、会话标识、课程或学生个人信息不进入自适应状态报告；报告只含倍率与匿名样本计数。
- 本功能不触碰真实写入适配器、批量并发提交、换 IP、多账号或任何破解验证逻辑。
- 真实开放时间、课程目录结构、提交与回读契约必须分别验收。离线测试通过不代表完成学校真实接入。

## 验收

在 `clients/windows/source` 中运行：

```bash
python -m unittest tests.test_adaptive_read_cadence -v
python -m unittest discover -s tests -p 'test_*.py'
```

检查未启用时保持旧行为；压力下只减速、不加速；逐步恢复；无数据不改变倍率；非法配置 fail-closed；调度器对所有课程每轮仍只有一次目录读取。

## 第二阶段：桌面运行状态（已提交，待合并验收）

Windows 首页「第 3 步 · 课程余量监测」新增只读状态行，显示当前启用状态、放缓倍率、压力样本数与正常样本数。worker 通过已有 Tk 事件队列发出匿名 `cadence` 事件；无需额外 HTTP 请求、不变更原有 status 事件元组、不影响课程状态或官方结果确认。具体网络请求耗时与预算等待仍可从现有脱敏延迟诊断报告查看。

**仍未实施**：学校正式写接口真实验收、自动选课实际提交、选择窗口可用性证明。Windows UI 的状态行只反映本机查询节奏，不代表选课成功率或服务端负载的直接测量。
